## What's New

MUSE 3.10 adds one working rule and the tools around it: while a feature is unfinished, keep
it on environments you own, and run PR, CI, review and release once, when it is done. It also
adds rules for automated gates, clearer memory search ranking and a scheduled-task check after
every account switch. The continuity runtime, installer and Stop hooks are unchanged.

### 🛠 Iterate on your own server

A new core skill, `iterating-on-own-server`, and ETHOS principle 6. Unfinished work is changed
and tested on L0 (local) or L1 (one integration preview at a fixed address). PR, CI and review
are production gates, not a development loop, so they run once per finished feature. The skill
covers the integration branch (never opens a PR, carries temporary commits), three checks before
showing anyone a build, when shipping early is acceptable, and what does not change: deployment
rules, production data procedure, payment and security review, secrets and deep QA.

### ⚖️ Gate eval discipline

`skills/core/muse-commands/references/GATE_EVAL_DISCIPLINE.md` sets five rules for every
automated judgment (identity, quality, semantic and voice checks, action classifiers):

- Tune on one set, judge once on a frozen exam set.
- Report misses and false blocks separately, by category, plus score distributions.
- Never leak the answer to the judge (file names, ids, labels); ground truth is labelled blind.
- Log one line per verdict: gate and version, input reference, verdict, score, latency, cost.
- Distil to a smaller model only after launch, and only if it is no worse on the exam set.

### 🔎 Clearer `recall.py` ranking

- Current memories come first, then memories whose frontmatter says
  `superseded_by: <newer-memory>` (marked in the heading), then pointer files such as
  `MEMORY.md` and `index-*`. A superseded memory cut by the line limit is named at the end
  instead of disappearing.
- `--why NAME` explains why a file is or is not near the top: keywords hit, the rule that put
  other files first, whether the line limit hid it, whether its successor matched.

### 🔁 Account relay rechecks scheduled tasks

Scheduled task files stay on the machine, but the app may list and run only the tasks created
by the signed-in account. Keep a manifest (task id, schedule, keep or stop, end date).
`/handoff save` updates it; on the new account `/handoff <lane>` compares the listed tasks with
the manifest and recreates every kept task that is missing and not past its end date.
